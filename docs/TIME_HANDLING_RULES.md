# Authoritative time handling

These rules apply to every API, backend service, database function, migration, and AI-generated change:

1. Never accept a client date/time as the value written to the database.
2. Every persisted real timestamp (`created_at`, `updated_at`, `opens_at`, `closes_at`, `read_at`, and similar) must be generated by PostgreSQL (`CURRENT_TIMESTAMP`, `NOW()`, or a database default) or by trusted server code using the server clock.
3. The client may send durations and intervals, expressed in game minutes. The server validates them and stores the duration, or derives the corresponding game deadline from authoritative server time.
4. The client may send read-only filters such as `from`, `to`, `before`, `after`, or a history window. Filters must never become persisted timestamps.
5. Game time is derived from the authoritative world clock (`earth_get_current_game_time()` / `world_state.genesis_at`). Never accept client-supplied `gameDay` or `gameMinute` for event creation, ledger entries, messages, proposals, settlements, or state transitions.
6. Processing work (cron, scheduler, worker restarts) must never advance or manipulate the world clock. World time determines what work is due; work does not advance time.
7. Daily settlement is tracked contiguously via `daily_settlement_control.settled_through_game_day`. Gaps in settlement history are never skipped.
8. The current open game day is never closed or settled (`lastClosedGameDay = currentGameDay - 1`).
9. Economic mutations requiring settled balances check `assertEconomyCaughtUp` and fail with HTTP `409` (`WORLD_SETTLEMENT_CATCHING_UP`) if settlement is catching up.
10. Calculate elapsed time from server/database timestamps in seconds. Under the canonical clock, one real second equals one game minute (`1,440 game minutes = 1 game day = 24 real minutes`).
11. Return authoritative timestamps, clock snapshot, and settlement cursor state in `/api/world` and `/api/health`.

Before adding a time-dependent API, verify: input classification (duration or filter), server-side clock source, database default/trigger, transaction consistency, replay behavior, and tests for client clock skew.
