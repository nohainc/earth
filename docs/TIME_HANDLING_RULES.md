# Authoritative time handling

These rules apply to every API, backend service, database function, migration, and AI-generated change:

1. Never accept a client date/time as the value written to the database.
2. Every persisted real timestamp (`created_at`, `updated_at`, `opens_at`, `closes_at`, `read_at`, and similar) must be generated by PostgreSQL (`CURRENT_TIMESTAMP`, `NOW()`, or a database default) or by trusted server code using the server clock.
3. The client may send durations and intervals, expressed in game minutes. The server validates them and stores the duration, or derives the corresponding game deadline from authoritative server time.
4. The client may send read-only filters such as `from`, `to`, `before`, `after`, or a history window. Filters must never become persisted timestamps.
5. Game time is derived from the authoritative world clock. Do not accept client-supplied `gameDay` or `gameMinute` for event creation, ledger entries, messages, proposals, settlements, or state transitions.
6. When a write needs both real time and game time, calculate both on the server in the same transaction. Real timestamps are for ordering and elapsed-second calculations; game minutes are for simulation rules.
7. Do not derive idempotency or business timestamps from the client wall clock. Correlation IDs must be opaque identifiers, not timestamps.
8. Calculate elapsed time from server/database timestamps in seconds. Under the current clock, one real second equals one game minute.
9. Validate duration ranges and overflow on the server; never trust client-calculated start, end, maturity, progress, or settlement times.
10. Return authoritative timestamps and calculated game-minute deadlines in API responses so the client renders the server result.

Before adding a time-dependent API, verify: input classification (duration or filter), server-side clock source, database default/trigger, transaction consistency, replay behavior, and tests for client clock skew.
